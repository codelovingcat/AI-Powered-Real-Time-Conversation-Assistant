# PII, transcript privacy and retention policy

**Scope:** This is an engineering policy grounded in the current repository implementation. It documents what Conversa stores and sends, what the application deletes, and what operators must configure outside the codebase. It is not a claim of legal or regulatory compliance and does not promise that external providers or infrastructure backups erase data on the application's schedule.

Treat spoken transcripts, typed requests, conversation instructions, summaries, translations, explanations and suggested replies as sensitive conversation content. Apply the same handling rules to text derived from that content.

## Data inventory

| Data | Where it is used or stored | Purpose and boundary |
| --- | --- | --- |
| Conversation metadata | Primary PostgreSQL database: conversation owner ID, title, instruction, source/target language, lifecycle state and timestamps | Reopen and manage an authenticated user's conversation. Access is owner-scoped. The instruction is user-authored text and must be treated as sensitive, not as harmless configuration. |
| Transcript and typed input | Message rows in the primary database, in `OriginalText` | Stores the other speaker's final recognized text and user formulation requests so history can be reopened. |
| AI-derived fields | The same message rows: translation, explanation, suggested answer and its translation, response/intent flags, provider name and prompt version | Displays the structured assistant result and supports product diagnostics at a non-content level. The text fields remain sensitive even when generated by an AI model. |
| Older-context summary | `ConversationContextSummaries` in the primary database | A bounded summary of older turns may be generated and reused with recent history. It is derived conversation content and is retained with the parent conversation. |
| Audio and live transcript updates | Active client/API memory and the configured speech-to-text provider during a live or one-shot transcription request | Audio chunks are forwarded to the configured STT provider; the application code does not write raw audio to its own conversation database or create an audio archive. Interim transcript updates are streamed to the client. This does **not** make a promise about the provider's handling or retention. |
| External AI requests | Gemini request body and response in transit | An assistant request can include the active instruction, latest input, language pair, up to 12 recent saved turns, and the older-context summary when included by the context builder. Summary refreshes send bounded older turns and the current summary. Text is sent because AI processing is the requested feature. |
| Identity/session data | Authenticated request context, short-lived access token in browser memory and an HttpOnly session cookie | Establishes the current user and authorized session. Token values, cookie values, claims and signing secrets must not be logged or added to telemetry. |
| Operational logs and telemetry | Application/platform logs; optional OTLP traces and metrics | Used to diagnose service health, provider failures and latency. They must not contain conversation content or credentials. Configured collectors and hosting platforms have their own access and retention controls. |
| Automated-test fixtures | Source-controlled test fixture `tests/Conversa.Api.Tests/Fixtures/ai-prompt-regression.json` and synthetic sentinel values in tests | Contains deliberately synthetic sample utterances and expected structured outputs. Real customer conversations, exported production rows, real identifiers and real credentials are not permitted in source control or CI fixtures. |

## Retention defaults

- **Live application database:** conversation metadata, messages and generated context summaries have no automatic time-to-live or scheduled expiry in the current application. The default is retention until the user explicitly deletes the conversation or a future documented product policy changes this behavior. Do not describe this as automatic deletion after a fixed number of days.
- **Conversation deletion:** `DELETE /api/conversations/{id}` removes the parent conversation and relies on database cascade rules to remove its saved messages and generated context summary. A missing ID and a non-owned ID receive the same empty HTTP 204 response. The application does not create a soft-delete row or archive. See [conversation deletion and data retention](conversation-deletion-retention.md).
- **Live audio and interim state:** the application does not persist raw audio as a conversation record. Audio and interim transcript state may exist in active client, server, socket or provider memory while processing. This is not a guarantee of immediate memory zeroization or of provider-side deletion.
- **Provider processing:** this repository does not configure or enforce retention periods for Gemini or Deepgram. Data received by a provider, along with provider-side diagnostics, abuse monitoring or recovery copies, is governed by the actual provider account settings and applicable contractual terms. Before accepting real user data in production, the service owner must verify and record those terms/settings; do not infer a no-retention guarantee from this code.
- **Database backups and recovery copies:** application deletion targets the live database. Backup expiry, snapshots, replicas and disaster-recovery copies are configured outside this repository, so no fixed backup retention duration is promised here. Operators must document and enforce backup retention and decide how deletion requests are handled after a backup restore; restoring an older backup can otherwise reintroduce a previously deleted row.
- **Logs and telemetry:** the repository does not define a universal log or OTLP retention period. The operator of each log destination and OTLP collector must configure access control and retention separately. Custom OpenTelemetry export is disabled by default; when enabled, traces and metrics are sent to the configured OTLP endpoint.
- **User deletion scope:** deleting a conversation does not delete the user's identity account, global assistant preferences, authentication session, a provider's already-received copy, or infrastructure-level backups. The repository does not currently implement identity-account deletion.

## Logging and telemetry rules

1. **Never log or export content.** Do not add original transcript text, typed requests, instructions, translations, explanations, suggested answers, summaries, audio payloads, raw provider request/response bodies, authorization headers, cookies, access tokens, API keys or database connection strings to logs, traces, metric attributes or error messages.
2. **Use a narrow operational allowlist.** Application-owned logs may record status codes, retry attempt, elapsed time, bounded provider error classification/code and exception type. The exception handler logs only the mapped HTTP status. These values diagnose failures without needing message content. Re-check new provider fields before logging them.
3. **Keep telemetry low-cardinality.** Custom telemetry uses provider, operation, outcome, input kind, prompt version and numeric counts/durations such as prompt character count and number of context turns. Do not add a user ID, conversation ID, transcript fragment, summary text, model prompt, or other content-derived label.
4. **Redact request locations before export.** ASP.NET Core and HttpClient instrumentation remove raw URL, path and query tags (including legacy URL attribute names). Where instrumentation supplies a route template, it may remain for low-cardinality grouping. Request/response bodies are not captured by the repository's instrumentation configuration.
5. **Keep detailed framework diagnostics off in production.** Do not enable HTTP body/header logging or Entity Framework sensitive-data logging in production. Scrub any platform-level request logs, exception telemetry and support bundles before granting access or sharing them outside the operations team.
6. **Protect destinations.** OTLP endpoints must use HTTPS outside Development and Testing. Give log collectors, OTLP backends, database backups and provider consoles access only to people/systems that need them, and set retention independently.
7. **Keep fixtures synthetic.** CI examples must be authored for tests or generated from synthetic values. Never copy a real transcript, support ticket, database dump, credential, or production trace into a fixture or commit history. Removing sensitive material in a later commit does not remove it from earlier Git history or existing clones.

The current provider unit tests include sentinel values that verify representative Gemini prompts/provider bodies and API keys do not leak into logged messages or surfaced provider exceptions. The HTTP telemetry URL-redaction behavior is also covered by a regression test. Keep those tests in place as providers or observability packages change.

## Production release checklist

- Verify and record Gemini and Deepgram data-processing/retention settings for the actual production account before real transcripts are sent.
- Set and document PostgreSQL backup/snapshot expiry, recovery access, and the process for honoring live deletion after restoration.
- If OTLP is enabled, confirm the endpoint is trusted, HTTPS-protected, access-controlled and configured with an explicit retention period.
- Review new log templates, exception mappings, tracing attributes and metric labels against the allowlist above.
- Keep prompt-regression fixtures synthetic and review CI artifacts for accidental body or secret output.
- Revisit this document whenever stored fields, AI/STT providers, provider settings, telemetry packages, or delete semantics change.
